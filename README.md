# usdm-acdc-in-practice

ICH M11, USDM v4.0 and the CDISC AC/DC framework — BC to DC to AC — learned by structuring one
protocol and taking two endpoints the whole way through, on a public simulated oncology trial.

**All nine stages are green on both endpoints, and Phase 2 is complete.**
[`NORTH.md`](NORTH.md) holds the destination, the scoreboards and the test; the scoreboards are
computed from the filesystem on every commit, so they cannot claim a stage that has not happened.

## Running it

Any machine, from a fresh clone:

```
git clone --recurse-submodules https://github.com/Lovemore-Gakava/usdm-acdc-in-practice.git
cd usdm-acdc-in-practice
python tools/bootstrap.py          # python3 on macOS/Linux; py -3 on Windows
```

`bootstrap.py` initialises the submodule, enables the pre-commit hook, builds `.venv` with a
Python 3.10+ interpreter, clones TORIVA-LUNG 301 at the pinned commit (sparse — 10 MB of 81),
and then runs `tools/check_alignment.py` to prove the result. It is idempotent, and `--check`
reports what is missing without changing anything.

Then, using the virtual environment's interpreter for anything that reads parquet:

```
.venv/bin/python tools/walkthrough.py serve     # app on :8080, guide at /walkthrough
.venv/bin/python tools/check_alignment.py       # P3 — 0 fail, 0 warn, 0 skip
```

On Windows that is `.venv\Scripts\python.exe`. Two things the bootstrap cannot do for you: a
CDISC Library key (`.cdisc-api-key` in the repository root, or `CDISC_API_KEY`) if you want the
app's concept Reference links to resolve rather than answer 401; and R, if you want to reproduce
stage 7's reference fits outside the engine — step 8 itself runs R in the browser under WebR and
needs nothing installed.

## What was done

Two endpoints, both nine-for-nine: **laboratory change from baseline** (ANCOVA) and **systolic
blood pressure change from baseline** (MMRM and ANCOVA). The second needed an `M.MMRM`
implementation written here, because upstream ships the method and the template and nothing to
run it with.

| Stage | Result |
|---|---|
| 0, 0b — **M11** | TORIVA's protocol mapped to the merged M11 elements, then restructured. M11 §3.1.1 requires the estimand *in the protocol*; TORIVA defers all five ICH E9(R1) attributes to the SAP, failing **25 required elements** across six objectives |
| 1 — **USDM** | `study/usdm/toriva-lung-301.usdm.json`, later regenerated from the M11 protocol — which took it from one estimand to six |
| 2, 3, 4 — **BC, DC, AC** | Seven TORIVA laboratory BCs on each measure terminal, `T.ChangeFromBaseline`, `T.CFB_ANCOVA` |
| 5 — **eSAP** | Generated by step 7. Its estimand is assembled from **two sources**: USDM gives the population summary and intercurrent events, the chain must give analysis population and treatment |
| 6 — **execution** | Step 8 via WebR against TORIVA's ADLB. ALT change from baseline at C2D1, torivumab − placebo = **−1.276** (SE 2.215, n = 429) |
| 7 — **comparison** | Does not match the same model on TORIVA's own `BASE` (−1.305). Every run reproduced to four decimals, and **68.6% of subjects** carry a different baseline row |

Both endpoints diverge from the built ADaM by the same rule — the engine takes the first row in
the Baseline window, TORIVA the `ABLFL` row — on 69% and 72% of subjects. That single mechanism,
found twice in two domains under two analyses, is the most useful thing the traverse produced.

The other two tiers were mapped and not authored: **ORR** composes at method level but its
authorable chain has `derivationChain: []`, and **PFS** does not compose on paper at all.

Eighteen discrepancies inside TORIVA itself surfaced from the mapping (D1–D18) — including one
that makes estimand E3 unimplementable as specified, and one where the SAP specifies no
laboratory analysis at all. They were filed upstream as
[#27](https://github.com/OpenTrialReporting/torivumab-nsclc-301/issues/27) and
[#53](https://github.com/OpenTrialReporting/torivumab-nsclc-301/issues/53), both closed, and the
study was regenerated. `study/source-refs.md` carries the register.

## Notes from the traverse

Thirteen findings came out of the mapping and the authoring, in
[`docs/findings/`](docs/findings/README.md) with the commands that establish each. They are
**by-products, not the product** — recorded when one blocked a stage, then left alone. Nothing
is being filed against `cdisc-org/analysis-concepts`.

Three are framework understanding rather than defect reports, and are the ones worth reading:

| | What it teaches |
|---|---|
| [F06](docs/findings/F06-no-general-predicate.md) | The outer boundary of what a DC can express — `M.ConditionalValue` is hardwired to `IF(IS_NA(…))`. This is what blocks PFS entirely |
| [F12](docs/findings/F12-baseline-flag-and-baseline-value-are-disconnected.md) | How the pipeline resolves a dependency: by output concept, exact string equality. A `Flag` can never satisfy a `Measure` |
| [F13](docs/findings/F13-authoring-surface-is-narrower-than-the-model.md) | Method ≠ transformation ≠ builder. **39 of 60 methods have no template**, and a chain is authored from templates |

The most transferable thing is not any single finding but the error rate. **Five had a premise
or a proposed fix disproved** — four after being drafted for public filing, and three failed the
same way: inferring what the application does from library JSON without running it. That is why
[`CLAUDE.md`](CLAUDE.md) requires the app to be served before a claim about it stands.
